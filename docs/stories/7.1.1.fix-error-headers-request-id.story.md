## User Story

**As** owner-operator testando Qwen3-Coder via VS Code Copilot BYOK durante o spike da Story 7.1,
**I want** que o gateway devolva o header `x-request-id` em **todas** as respostas — sucesso *e* erro (401, 404, 413, 429, 502, 503) — e que o frame SSE de erro mid-stream carregue o mesmo campo,
**so that** o cliente Copilot BYOK deixe de crashar com `Cannot read properties of undefined (reading 'headerRequestId')` quando o POD Qwen estiver momentaneamente indisponível (cold start, transição do scheduler, hiccup de rede), permitindo que um 502 transiente vire retry limpo em vez de erro fatal de cliente.

## Context

### Why this story exists now

Commit `07a6a2c` (2026-07-27 17:05 GMT-3) alegou corrigir o crash do cliente adicionando `x-request-id` + `system_fingerprint`, mas **só cobriu os paths de sucesso** (`generate.ts:321` streaming 200 e `generate.ts:354` JSON 200). Todos os paths de erro continuam sem o header:

- `generate.ts:583` `generateError()` → `openaiErrorResponse()` retorna 400/401/404/413/429/502/503 sem `x-request-id`
- `generate.ts:597` `withGenerateHeaders()` → 401 auth failure sem `x-request-id`
- `openai-error.ts:99` `openaiErrorResponse()` só aceita `extraHeaders` que os call sites não passam
- `openai-error.ts:139` `openaiStreamErrorFrame()` → erro SSE mid-stream não carrega o campo

Cenário observado (VS Code Copilot BYOK, 2026-07-27 ~17:07 GMT-3):
1. VS Code envia request → gateway
2. Upstream (POD Qwen) retorna 5xx (cold start / Ollama unhealthy)
3. `forwardToTextEndpoint` lança `TextUpstreamError('http_5xx')`
4. `handleGenerateUpstreamError` → `generateError(502, 'upstream_error', ...)` → response **sem** `x-request-id`
5. VS Code lê `.headerRequestId` → `undefined` → crash
6. VS Code retenta 5× (32.24s total), mesmo path, mesmo crash

O 502 upstream em si é *aceitável* (cold-start do modelo 30B leva 30-60s; scheduler faz start/stop diário). O crash do cliente é o defeito real — ele mascara instabilidade upstream como "cliente quebrado" e impede fallback/retry limpo.

### What this story produces (NEW — additive-only)

Todas as mudanças são additive-only sobre headers/frames — nenhum path de sucesso muda de comportamento.

1. `generate.ts:583` `generateError()` — passa a receber `completionId` e injeta `x-request-id: {completionId}` nos extraHeaders passados a `openaiErrorResponse()`.
2. `generate.ts:597` `withGenerateHeaders()` — mesma injeção no path 401 auth failure (gera `completionId` local se necessário, para manter correlação).
3. `generate.ts:handleGenerate` — thread do `completionId` (já existe em `generate.ts:194`) por todos os call sites de `generateError`.
4. `openai-error.ts:139` `openaiStreamErrorFrame()` — passa a receber `completionId` opcional e inclui `id: {completionId}` no envelope de erro SSE (paridade com o `id` do chunk normal).
5. Testes de regressão em `gateway/tests/generate.test.ts` (ou novo `gateway/tests/error-headers.test.ts`) — 3+ asserts confirmando que responses 401/429/502/503 carregam `x-request-id`.
6. Redeploy do Worker via `@devops` após merge local.

### Architectural reuse (Article IV-A — REUSE > ADAPT > CREATE)

- **REUSE**: função `generateChatCompletionId()` (`generate.ts:66`) — o mesmo `chatcmpl-{uuid}` gerado no início da request serve para o header de erro (correlação logs ↔ cliente).
- **REUSE**: assinatura `openaiErrorResponse(code, extraHeaders)` — já aceita `extraHeaders`; call sites é que não passam. Zero mudança na assinatura pública.

## Acceptance Criteria

1. **`x-request-id` presente em respostas de erro OpenAI-shaped**
   Toda response gerada por `openaiErrorResponse()` a partir de um call site em `handleGenerate` inclui header `x-request-id` cujo valor é o `completionId` (`chatcmpl-<uuid>`) gerado no início do request. Cobre no mínimo: 400 (`invalid_json`), 401 (`invalid_api_key`), 404 (`model_not_found`), 413 (`request_too_large`), 429 (`rate_limit_exceeded`), 502 (`upstream_error`), 503 (`upstream_unavailable`).

2. **`x-request-id` presente em auth failure early-return**
   O path `validateAuth` (`withGenerateHeaders` em `generate.ts:597`) também emite `x-request-id`. Como este path pode disparar antes de a request body ter sido lida, `completionId` é gerado no início de `handleGenerate` (já é) e reusado aqui.

3. **`id` presente no envelope de erro SSE mid-stream**
   `openaiStreamErrorFrame(code)` passa a aceitar `completionId?: string` e emite `{"error": {...}, "id": "{completionId}"}` no frame `data:` — paridade com o `id` que envelopeStream já injeta em chunks de sucesso.

4. **Regressão coberta por testes**
   Ao menos 3 testes novos em `gateway/tests/` afirmam:
   - (a) Response 502 (upstream 5xx simulado) contém header `x-request-id` matching `/^chatcmpl-[a-f0-9-]{36}$/`.
   - (b) Response 429 (rate limit exceeded — gemma4:e4b, budget esgotado no KV mock) contém header `x-request-id`.
   - (c) Response 401 (API key inválida) contém header `x-request-id`.
   Testes existentes continuam passando (191 → 194+).

5. **Success paths intactos (regressão zero)**
   Testes existentes que validam success paths (`generate.test.ts`, `openai-compat.test.ts`, `sse.test.ts`) continuam passando sem modificação. `x-request-id` continua sendo o `completionId` gerado no início do request — mesmo valor que o `id` dentro do body.

6. **Deploy validado empiricamente**
   `@devops` faz redeploy do Worker via `wrangler deploy` e valida com `curl -D -` que:
   - Uma request forçando 429 (Bearer inválido → 401) retorna header `x-request-id: chatcmpl-*`
   - Uma request forçando 502 (endpoint inválido temporariamente) retorna header `x-request-id: chatcmpl-*`
   Owner faz smoke test manual no VS Code Copilot BYOK: dispara request quando POD está em cold-start e confirma que o erro aparece como retry-recuperável, sem crash de cliente.

### Technical constraints

- **Case do header**: HTTP headers são case-insensitive. Emitir como `x-request-id` (lowercase, consistente com commit `07a6a2c` e RFC 9110). Cliente VS Code lê via SDK Node, que normaliza para lowercase.
- **Formato do valor**: `chatcmpl-<uuid v4>` — mesmo formato do `id` no body. Padrão OpenAI (`chatcmpl-*` sem constraint estrito no lado do cliente, mas mantém convenção).
- **Correlação com logs**: `completionId` já vai para log via `log()` calls (`generate.ts:262,344`) — cliente pode reportar o `x-request-id` e a gente correlaciona com wrangler tail. **Não mudar formato**.
- **Backward compat**: `openaiErrorResponse(code, extraHeaders)` já aceita extraHeaders — não mudar assinatura. Só passar mais campos no objeto.

### Testing

Estratégia: unit tests em Vitest com mocks de KV e `forwardToTextEndpoint`. Padrão já usado em `gateway/tests/rate-limit-tokens.test.ts` e `gateway/tests/openai-compat.test.ts`.

Sample skeleton (referência — não copiar cegamente):

```ts
import { describe, it, expect, vi } from 'vitest';
import { handleGenerate } from '../src/generate.js';
import * as textForwarder from '../src/runpod-text.js';

describe('error responses include x-request-id header', () => {
  it('502 upstream_error carries x-request-id', async () => {
    vi.spyOn(textForwarder, 'forwardToTextEndpoint').mockRejectedValue(
      new textForwarder.TextUpstreamError('boom', 'http_5xx', 500),
    );
    const req = new Request('https://gw/v1/chat/completions', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'X-API-Key': 'valid-key' },
      body: JSON.stringify({ model: 'gemma4:e4b', messages: [{ role: 'user', content: 'hi' }] }),
    });
    const res = await handleGenerate(req, mockEnv());
    expect(res.status).toBe(502);
    expect(res.headers.get('x-request-id')).toMatch(/^chatcmpl-[a-f0-9-]+$/);
  });
  // ...429 e 401 análogos
});
```

Sem mock de `Date.now()` — `crypto.randomUUID()` no runtime do teste basta.
